# Real Document Validation Runbook

This runbook creates a clean validation environment without deleting the
existing Build 1 demo/test data. It does not change extraction, verification,
or export behavior.

## Runtime Storage Map

### Local development

Run backend commands from `order-assurance/backend`.

| Data | Configuration | Default resolved path |
| --- | --- | --- |
| SQLite database | `DATABASE_URL=sqlite:///./order_assurance.db` | `backend/order_assurance.db` |
| Uploaded PDFs | `STORAGE_DIR=storage/documents` | `backend/storage/documents/<bundle-id>/` |
| Preview PNGs | Generated by `GET .../preview/pages/...png` | Not persisted; returned from memory |
| OCR page images | Generated by PyMuPDF | Not persisted; sent from memory |
| XLSX exports | Generated by `BytesIO` | Not persisted server-side; browser/test download location only |

The SQLite path is relative to the process working directory. Starting the
backend outside `backend/` without an absolute `DATABASE_URL` can create a
different database accidentally.

### Docker

| Data | Container path | Docker volume |
| --- | --- | --- |
| PostgreSQL database | `/var/lib/postgresql/data` | `order-assurance_order_assurance_pg` |
| Uploaded PDFs | `/app/storage/documents` | `order-assurance_order_assurance_storage` |

The active Compose project mounts the storage volume at `/app/storage` and the
database volume at `/var/lib/postgresql/data`. Preview PNGs, OCR renderings, and
XLSX exports are not stored in either volume.

## Backup Existing Data

Stop user activity before taking a backup. Do not run `docker compose down -v`,
`odmp.ps1 reset`, or any recursive cleanup command before the backup is
verified.

### Local SQLite and uploads

From `order-assurance`:

```powershell
$stamp = Get-Date -Format "yyyyMMdd-HHmmss"
$backup = "backups\build1-local-$stamp"
New-Item -ItemType Directory -Path $backup | Out-Null

# Stop the local backend before copying SQLite.
Copy-Item backend\order_assurance.db "$backup\order_assurance.db"
Compress-Archive -Path backend\storage\* -DestinationPath "$backup\storage.zip"

Get-Item "$backup\order_assurance.db", "$backup\storage.zip"
Get-FileHash "$backup\order_assurance.db", "$backup\storage.zip"
```

There are no server-side preview/cache/export folders to back up. Preserve any
downloaded XLSX files separately if they are validation evidence.

### Docker PostgreSQL and uploads

From `order-assurance`, with the existing stack running:

```powershell
$stamp = Get-Date -Format "yyyyMMdd-HHmmss"
$backup = "backups\build1-docker-$stamp"
New-Item -ItemType Directory -Path $backup | Out-Null

docker compose exec -T database pg_dump `
  -U order_assurance -d order_assurance -Fc `
  -f /tmp/order_assurance.dump
docker compose cp database:/tmp/order_assurance.dump "$backup\order_assurance.dump"

docker compose exec -T backend tar -C /app/storage -czf /tmp/storage.tgz .
docker compose cp backend:/tmp/storage.tgz "$backup\storage.tgz"

Get-Item "$backup\order_assurance.dump", "$backup\storage.tgz"
Get-FileHash "$backup\order_assurance.dump", "$backup\storage.tgz"
docker compose exec -T database pg_restore -l /tmp/order_assurance.dump |
  Select-Object -First 10
docker compose exec -T backend tar -tzf /tmp/storage.tgz |
  Select-Object -First 10
```

Keep the dump and storage archive together because database document rows refer
to files in the storage volume.

## Recommended Clean Validation Run

### Option A: isolated local SQLite runtime

This is the lowest-risk option. It creates a new database and upload directory
under ignored `validation-runs/`; existing local and Docker data is untouched.

```powershell
cd order-assurance

# If the Docker stack is running, stop containers but preserve volumes.
docker compose down

.\scripts\new-validation-run.ps1
```

The script runs migrations and prints the exact activation and start commands.
In the backend terminal:

```powershell
. .\validation-runs\<run-name>\activate.ps1
cd backend
python -m uvicorn app.main:app --host 127.0.0.1 --port 8100
```

In a second terminal:

```powershell
cd order-assurance\frontend
$env:VITE_API_BASE_URL="http://127.0.0.1:8100/api"
npm run dev
```

After the local validation run, restore the original Docker stack with
`docker compose up -d`.

### Option B: isolated Docker volumes

Compose project names isolate named volumes. This creates a clean PostgreSQL
database and clean upload volume while retaining the current Build 1 volumes.

```powershell
cd order-assurance

# Preserve existing volumes; do not add -v.
docker compose down

# Start a separate project with new named volumes.
docker compose -p order-assurance-validation up -d --build
docker compose -p order-assurance-validation exec -T backend `
  python -m app.migrations.runner up
```

Use `http://127.0.0.1:5180/bundles`. When finished:

```powershell
docker compose -p order-assurance-validation down

# Restore the Build 1 stack using its original volumes.
docker compose up -d
```

Do not use `down -v` if validation results need to be retained.

## Guarded Reset of Shared Local Runtime

Prefer an isolated run. If the shared local SQLite runtime must be reset:

1. Stop backend and frontend processes.
2. Complete and verify the local backup above.
3. Move, rather than delete, the current runtime paths.
4. Run migrations.
5. Start backend and frontend.

```powershell
cd order-assurance
$stamp = Get-Date -Format "yyyyMMdd-HHmmss"
$quarantine = "backups\pre-reset-$stamp"
New-Item -ItemType Directory -Path $quarantine | Out-Null

Move-Item backend\order_assurance.db "$quarantine\order_assurance.db"
Move-Item backend\storage "$quarantine\storage"
New-Item -ItemType Directory -Path backend\storage\documents -Force | Out-Null

cd backend
python -m app.migrations.runner up
python -m uvicorn app.main:app --host 127.0.0.1 --port 8100
```

The move commands are intentionally manual. Confirm `$quarantine` is correct
and the copied backup is readable before running them.

## Migration Commands

Local SQLite, from `backend`:

```powershell
python -m app.migrations.runner up
```

Docker:

```powershell
docker compose exec -T backend python -m app.migrations.runner up
```

The migration runner is a lightweight single-file SQL runner, not Alembic. It
does not maintain a migration version table.

## Sample Set Layout

Use `sample/real-validation/sample_set_01/`:

```text
sample_set_01/
  customer_po.pdf
  company_invoice.pdf
  delivery_challan.pdf
  company_po_to_vendor.pdf
  vendor_invoice.pdf
  expected.json
```

Only use approved, redacted PDFs. Do not overwrite or relocate the existing
files under `sample/extracted/`.

## Validation Checklist

1. Confirm the clean database has no bundles.
2. Copy or reference one approved sample set; do not modify source PDFs.
3. Complete `expected.json` from a human review before extraction.
4. Create one bundle in `/bundles`.
5. Upload all five PDFs using the matching document slots.
6. Open each PDF preview and confirm page count/readability.
7. Run extraction for each document.
8. Capture each document response and extracted field values.
9. Compare values, confidence, evidence, and missing fields with
   `expected.json`.
10. Record manual corrections separately; do not silently update the oracle.
11. Open Verification and capture every check result, source, and severity.
12. Compare verification status/checks/issues with `expected.json`.
13. Download the XLSX export into the run's `downloads/` folder.
14. Inspect the six expected sheets and compare values with both the API
    responses and `expected.json`.
15. Save extraction responses, verification summary, audit events, XLSX, and
    observations under the run's `artifacts/` folder.

The persisted Build 1 audit trail currently records manual extracted-data
corrections only. Upload, extraction, re-extraction, verification-summary, and
export activity is written to structured application logs but not to the
`audit_events` table. A run with no manual correction is therefore expected to
return an empty audit-event list.

## Risks

- `odmp.ps1 reset` runs `docker compose down -v` and deletes both Docker named
  volumes. Do not use it for validation setup.
- SQLite database paths are working-directory relative unless made absolute.
- Database and upload storage must be backed up/restored as a pair.
- Preview PNGs and XLSX exports are ephemeral unless the client saves them.
- Real PDFs may contain sensitive data; keep them redacted and outside source
  control.
- The migration runner splits SQL on semicolons and has no version table.
- Existing cleanup tooling is not part of this runbook; avoid it for creating a
  clean validation environment.
