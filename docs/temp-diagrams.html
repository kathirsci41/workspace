DPP Chain Validation — Architectural Approaches

Comparing Approach B (Reference Enrichment) vs Approach C (Explicit Chain Groups)

Approach B — Reference Enrichment RECOMMENDED

Minimal migration · CPO-centric preserved
erDiagram PurchaseOrder ||--o{ Document : "po_id" PurchaseOrder ||--o{ VendorPO : "po_id" PurchaseOrder { int id PK string po_number string so_number string billing_type string scenario json billing_milestones } Document { int id PK int po_id FK string doc_type string so_number "NEW" string vpo_number "NEW" int billing_stage "NEW" json extracted_data } VendorPO { int id PK int po_id FK string vpo_number string vendor_name }
Pros
  • 3 new columns only
  • No UI redesign needed
  • Works without ERP
  • Chain queries via so_number
Cons
  • SO not a first-class entity
  • Multi-SO per CPO needs join logic
  • Chain state lives in query, not model

Approach C — Explicit Chain Groups

Most flexible · Extra abstraction layer
erDiagram PurchaseOrder ||--o{ DocumentChain : "po_id" PurchaseOrder ||--o{ Document : "po_id" DocumentChain ||--o{ DocumentChainMember : "chain_id" Document ||--o{ DocumentChainMember : "document_id" PurchaseOrder { int id PK string po_number string scenario string billing_type } DocumentChain { int id PK int po_id FK string chain_ref string chain_type string status json required_docs } DocumentChainMember { int id PK int chain_id FK int document_id FK string role bool is_validated } Document { int id PK int po_id FK string doc_type json extracted_data }
Pros
  • Chain is a real model object
  • Easy to query chain status
  • Handles any grouping key
  • Per-document validation roles
Cons
  • 2 new tables + migration
  • Chain creation must be triggered
  • More code to write and test
