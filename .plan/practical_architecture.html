The Core Practical Question: DiT + LayoutLMv3 Separately, or LayoutLMv3 Only?

Previous architecture showed DiT layout analysis as a separate step before LayoutLMv3. Practically, for 6 known document types, LayoutLMv3 handles layout implicitly through spatial embeddings. Here is the honest comparison of all three options.

Option A: DiT then OCR then LayoutLMv3

3 model calls — complex

Separate layout zone detection, then OCR per zone, then LayoutLMv3 extraction.

  • Best for completely unknown document layouts
  • DiT catches complex multi-column structures
  • 3 separate model inference calls per document
  • Latency compounds: DiT 200ms + OCR 30s + LM 500ms
  • More to deploy, maintain, version
  • Overkill for your 6 known document types

Option B: OCR then LayoutLMv3 only — Recommended

2 model calls — start here

qwen2.5vl outputs text plus coordinates. LayoutLMv3 handles layout and extraction in one pass.

  • LayoutLMv3 spatial embeddings handle layout implicitly
  • 2 model calls, not 3 — lower latency
  • Fine-tuned on your docs — knows your layouts
  • Simpler to deploy, debug, iterate
  • May need DiT later for novel vendor layouts

Option C: End-to-End (Donut, GOT-OCR 2.0)

1 model call — future path

Single model takes document image, outputs structured JSON directly. No intermediate OCR.

  • One model call for everything
  • No error propagation between layers
  • Needs significantly more fine-tuning data
  • Harder to debug when wrong
  • Cannot use PyMuPDF digital fast path

What BIO Token Classification Means in Practice

LayoutLMv3 processes the document as a word sequence. Each word token gets classified: B-invoice_number (beginning), I-invoice_number (continuation), or O (not a target field). The model learns these patterns from your fine-tuning data. For example: the token "1ITR2526..." appearing top-right, after "Invoice No.:" → classified as B-invoice_number. Spatial position is encoded as normalized coordinates (x1/1000, y1/1000, x2/1000, y2/1000). This spatial encoding is why it outperforms a pure text LLM on documents with consistent visual layouts.

Honest Practical Assessment — What Will Actually Be Hard

The architecture is sound. These are the real challenges going from diagram to working production code.

1

Getting Bounding Boxes Out of qwen2.5vl

LayoutLMv3 needs text with (x1, y1, x2, y2) coordinates. qwen2.5vl has a grounding mode for this but it is not the default — you need a specific prompt and a coordinate output parser. This is the most critical integration point. If Layer 1 cannot reliably output coordinates, LayoutLMv3 loses its main advantage. For the digital path (PyMuPDF), coordinates come free and are perfectly precise — this is why the hybrid router unlocks so much value.

Plan: 2-3 days to validate qwen2.5vl grounding output format and build coordinate parser
2

How Much Verified Data Do You Actually Have?

LayoutLMv3 fine-tuning needs labelled examples. Minimum for meaningful results: 100-200 per document type. If you have only 20 verified COMPANY_DC documents, the fine-tuned model for that type will overfit. Run this query first: SELECT document_type, COUNT(*) FROM document_metadata WHERE status='VERIFIED' GROUP BY document_type. If counts are low, start with LayoutLMv3 in zero-shot mode using its existing pretraining — it still outperforms qwen2.5:7b — and fine-tune incrementally as verified documents accumulate from the HITL loop.

Plan: Run the count query before committing to fine-tuning timeline
3

Phase 0 Must Come First — Training Data Is Currently Dirty

Every verified document in your database was extracted with 768px cap, 200 DPI, and page 1 only. That means your training data has OCR errors baked in. The correct order is: Phase 0 fixes today (35 min), then re-extract all existing documents with corrected settings, then let humans re-verify the now-more-accurate extractions, THEN use those clean re-verified extractions as training data for LayoutLMv3. If you skip this and train on the dirty labels, you will fine-tune LayoutLMv3 to reproduce your old OCR errors.

Plan: Phase 0 fixes first, then re-extract all, then re-verify, then LayoutLMv3 training
4

PyMuPDF Digital Detection Has Edge Cases

The character count heuristic works for 90% of cases. Edge cases include: DRM-protected PDFs with corrupted text layers, PDFs embedding text as vector graphics, vendor invoices that are digital PDFs but with hand-stamped overlays (RECEIVED stamp, signature). Handle these incrementally as you encounter them in production — do not try to solve all edge cases upfront. Log every routing decision so misroutes are visible and debuggable.

Plan: Start with simple heuristic, log misroutes, fix edge cases iteratively
5

Document Classifier Training — Check Visual Distinctiveness First

The 6-class document classifier works well only if your document types are visually distinct from each other. VENDOR_INVOICE and COMPANY_INVOICE might look similar in layout. Before training, print a few examples of each type side by side and check whether YOU can tell them apart visually at a glance. If you cannot, the classifier cannot either. In that case, use visual similarity for initial classification and fall back to text-content heuristics (does the document contain "1ITR" prefix? must be COMPANY_INVOICE) as a secondary signal.

Plan: Visual inspection first, then classifier training if types are visually distinct
